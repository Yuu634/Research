# 擬似編曲前後ペアの作成

trainに自己再構成ペアを追加する場合は、[再構成データの作成規約とCLI](../../docs/PAIRDATA_RECONSTRUCTION.md)を参照する。
`reconstruction.py`が別の出力先へ追加し、元pairdataと評価用シャードを保持する。

ユーザー提示の「擬似編曲前後ペア作成アルゴリズム」の8段階を実装した。
難易度ベクトルはユーザー指定により、[承認済みv2](../../docs/ATTRIBUTE_FORMULA_REVIEW.md)の
`s_tech, s_indep, s_hand, s_foot, s_move` を使用する。
`s_rhythm` は参考値として保存し、難→易の方向付けや難易度差へは加えない。
既存の曲から異なる小節を検索する方式で、音符をランダムに編集してペアを増やす方式ではない。

## 配置

データ作成コードを `data/` 内に置くという今回の指示に従い、packageとしてまとめた。
リポジトリ直下で `python -m data.pairdata...` を実行する。

| ファイル | 役割 |
|---|---|
| `core.py` | 特徴抽出、候補検索、音楽的類似度、難易度の方向付け |
| `build.py` | 原譜の検証、並列抽出、再開、重複除外、シャード出力 |
| `validate.py` | 全ペアの原譜・数値・分割を再検証 |
| `io.py` | 圧縮PKL、JSON、ハッシュ、学習用の逐次読み込み |

`.gitignore` はこのpackageのPythonとMarkdownだけを例外にしている。
生成データ、重み、ログ、Pythonキャッシュはコミットしない。

## 図の各段階との対応

### 1・2：データ入力と小節分割

入力は `data/processed/drum_collection_difficulty_v2/` の35,106曲。
元の有効train/val/test/itest分割と、v2のクラス境界・生スコアを使用する。
元のPKLチェックサムとラベル／生スコアの対応を確認してから処理する。
各小節は4/4・96位置。末尾小節も処理し、元トークンをそのまま切り出してEOSを付ける。
v2の前段で除外した48,496曲を復帰させる処理は含まない。

### 3：特徴抽出

- **難易度**：v2の5属性クラスを7で割ったベクトル。生の連続スコアも保持する。
- **リズム**：Kick／Snare・Rim／Hi-hat（開閉・ペダル）／その他の4群×96位置の打点有無。
- **骨格**：Kick、Snare、Accentの3系列。Kickは四分音符位置の重み2・その他1。
  Snareは第2・第4拍頭の重み3・その他1。Accentは元トークンに明示されたものを重み1とする。
  弱拍のKick・Snareも系列に残す。
- **文脈**：曲ID、局所32小節ブロック、小節番号を4で割った余り、Fill代理フラグ、前後1小節。

図のChorus等に相当する正解の区間名は入力にないため、`section=null` とする。
局所ブロックや4小節周期を、実際に検出したセクション・フレーズとは呼ばない。
Fill代理フラグは「タムが2打以上、または最終拍が4打以上かつ他3拍平均の2倍以上」。
これも人手によるFill判定ではない。

骨格の定義・閾値・窓幅は今回の運用上の仮定であり、学習済みの認識器や検証済みの音楽的正解ではない。

### 4：候補小節の抽出

同一曲・同じ局所32小節ブロック・同じ4小節周期位置・同じFill代理フラグ・同じBPMの小節を候補にする。
曲をまたいだ検索や、拍の回転・タイムシフト・テンポ変更による一致は使用しない。
窓の外にある類似小節を網羅する検索ではない。

次は小節単位で候補から除く。

- 音符数が4未満。
- 現在小節または直前小節に同一位置・同一楽器の重複がある。
- 連続スコアが非有限。
- 手の負荷が32打／秒相当を超える、または足の負荷が20打／秒相当を超える。
- Kick・Snareの骨格打点がない。

速度上限は極端な入力を抑える運用上の設定で、演奏可能性を保証する境界ではない。

### 5：音楽的類似度

各系列の類似度は、重み付き打点列について `2 × sum(min(a,b)) / (sum(a)+sum(b))` を使う。
両方に打点のない楽器群は平均から除き、全群が空なら類似度0。

| 成分 | 内部の群の重み | 採用下限 |
|---|---|---:|
| リズム `S_rhythm` | Kick .35、Snare .35、Hi-hat .20、その他 .10 | 0.70 |
| 骨格 `S_skeleton` | Kick .45、Snare .45、Accent .10 | 0.90 |
| 文脈 `S_context` | 直前同士・直後同士のリズム類似度の平均 | 0.70 |

曲端で片方だけ前後小節が欠ける場合、その側の文脈類似度は0。
総合値は `q = .30 S_rhythm + .50 S_skeleton + .20 S_context` とし、**q > .85** を要求する。
下限・重みは結果に合わせて自動調整しない。qはルールに対する類似度であり、正しい編曲である確率ではない。

### 6・7：難易度差と編曲前後の向き

編曲後の5属性が、編曲前よりすべて同じか低い場合に限る。
クラスだけでなく、元の連続スコアについても各属性の非増加を要求する（浮動小数の許容誤差1e-9）。
正規化した5属性ベクトルのユークリッド距離は **0.20より大きい** ことを要求する。
一方の属性を下げる代わりに別の属性を上げるペアは、この版では採用しない。

v2の難易度は直前小節にも依存するため、編曲後候補を**編曲前の直前小節へ接続し直して再計算**する。
再計算後も5属性が増えず、十分な差があることを要求する。
保存する `d_after` と `raw_after` はこの再接続後の値。候補の元の文脈での難易度も別項目で残す。
現在小節の演奏後に続く小節の難易度変化は、この判定の対象に含めない。

クラスは順序尺度で、クラス間隔を心理的難易度の等間隔として検証したわけではない。
このベクトル距離はペア選択の運用上の条件である。

### 8：重複除外と出力

曲内では、同じ打点・強弱・奏法の前後組を1ペアにまとめる。
q、難易度差、小節番号の順に順位を固定し、編曲前1小節につき最大4ペア、1曲につき最大256ペアとする。
反復回数をそのまま学習例数へ変換していない。

全体でも同じペアを除外する。さらに、**編曲前・後の現在小節の内容署名が分割間で共有されない**よう、
`itest → test → val → train` の順で既存分割を優先する。
内容署名はテンポとトークンの並び順を除き、打点位置・楽器・強弱・奏法を含む。
別分割で既に採用された現在小節を含むペアは、曲の所属を変えることなく除外する。
これはペアだけの重複除外より厳しい条件である。

前後の文脈小節の共有、近似重複、原曲単位の近縁性までは除外していない。
評価用の難易度境界はv2のtrainで確定済みのものをそのまま使用し、評価結果で再推定しない。
分割ごとの件数やジャンル分布を均等にする処理も行っていない。

## 出力形式と読み込み

既定出力は `data/processed/drum_pairdata_v1/`。

| パス | 内容 |
|---|---|
| `shards/<split>-NNNNN.pkl.gz` | ペア辞書のリスト。最大4,096ペア／シャード |
| `index.json` | 分割、シャード名、件数、SHA-256 |
| `identity.json` | 入力とコードのハッシュ、設定、実行パス |
| `summary.json` | 採用・除外、属性差、平均スコアの集計 |
| `validation.json` | 全ペアの検証結果 |
| `sources.jsonl` | 採用元の曲の来歴・ライセンス・ハッシュ |
| `piece_audit.jsonl` | 全入力曲の候補数・採用数・除外理由 |
| `bounds.json`, `drum_vocab.pkl` | 使用したv2境界と語彙 |

各ペアには次を保存する。

- `X_before`, `X_after`：元のstandard小節トークンID列＋EOS。`bar_positions=[0]`。
- `d_before`, `d_after`, `delta_d`：5属性、0〜1、差分は **after − before**。
- `difficulty_before`, `difficulty_after`：6属性の整数クラス。6番目は参考値。
- `raw_before`, `raw_after`：同順の6連続スコア。
- `original_after_raw`, `original_after_classes`：編曲後候補の元の文脈での値。
- `q`, `similarities`, `difficulty_distance`：総合・成分類似度と難易度差。
- `source`：曲ID、分割、データセット、前後小節番号、原データ／入力PKLのハッシュ、ライセンス。
- `context`：区間名の欠損、文脈代理情報、編曲前の直前・直後トークン、候補の元の前後トークン。
- `pair_id`, `before_pattern`, `after_pattern`：再現・重複検査用の内容署名。

```python
from data.pairdata.io import iter_pairs

for pair in iter_pairs('data/processed/drum_pairdata_v1', split='train'):
    x_before = pair['X_before']
    x_after = pair['X_after']
    target_difficulty = pair['d_after']
    delta = pair['delta_d']
```

これは編曲前後のペア形式で、従来の自己再構成用 `DrumTransformerDataset` へそのまま渡す形式ではない。
ペアを利用する学習ループへの接続・モデル学習は本タスクの範囲外。
訓練時の前後文脈の使用有無は学習目的に合わせて明示すること。

## 実行と再開

既存のNumPyと標準ライブラリで動作する。追加ダウンロードは不要。

```bash
python -m data.pairdata.build --help
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 \
  python -m data.pairdata.build --workers 24
python -m data.pairdata.validate --workers 24
```

`--stage mine / package / validate / all` で段階を指定できる。
既定の作業領域 `data/work/drum_pairdata_v1/` に64曲単位の候補バッチとチェックサムを保存する。
同じコマンドは検証済みバッチから再開する。入力・コード・設定が変わった場合は、
別の `--output` と `--work` を指定する。入力データ・v2スコアDBは実行中に変更しない。
中断直後のシャードや索引を学習に使わず、全件検証が成功した出力を使用する。

試験例：

```bash
python -m data.pairdata.build --limit-per-group 20 --workers 8 \
  --batch-size 20 --shard-size 256 \
  --output output/pairdata_v1/smoke --work output/pairdata_v1/smoke_work
```

閾値等は `Config` の項目をJSONに書き、`--config` で指定できる。
採用数が少ない場合でも、件数目標のために自動で閾値を緩めない。

## 実施結果（2026-09-30）

35,106曲・3,256,333小節を処理し、6,597,123組を比較した。
品質条件を満たす小節は2,431,340。曲内選定後の82,924ペアから、
全体重複・分割間共有を除き、**50,222ペア**を生成した。採用元は10,857曲。

| データセット | train | val | test | itest | 合計 |
|---|---:|---:|---:|---:|---:|
| groove | 2 | 0 | 0 | 0 | 2 |
| groove2groove | 5,277 | 68 | 50 | 76 | 5,471 |
| lakh | 32,725 | 5,361 | 6,663 | 0 | 44,749 |
| 合計 | 38,004 | 5,429 | 6,713 | 76 | 50,222 |

15シャード、圧縮PKL合計15,933,475バイト。全50,222ペアの検証は成功（終了コード0）。
元の音符列、原文脈と再接続後の難易度、類似度、クラス、分割とチェックサムを全ペアで確認した。
現在小節の内容署名57,709種類は分割間で重複せず、ペアの完全一致も0件。
学習用の逐次読み込みでも全4分割・50,222ペアを確認した。

全体の完全一致ペア除外は18,218組、別分割の現在小節を共有するための除外は14,484組。
候補段階では、元の難易度では簡略化に見えても再接続後に条件を満たさない46,608組を除外した。
平均qは0.945533、平均難易度距離は0.466363。これらは採用条件下の指標で、編曲の正解率ではない。

| 下がった属性 | 該当ペア数 | 全ペア中の割合 |
|---|---:|---:|
| s_tech | 24,264 | 48.3% |
| s_indep | 18,946 | 37.7% |
| s_hand | 16,938 | 33.7% |
| s_foot | 5,522 | 11.0% |
| s_move | 15,058 | 30.0% |

複数属性が下がるペアがあるため、属性別件数は重複する。上がる属性を含むペアは0件。

**Lakhへの偏りが大きく、Grooveのペアは2件のみ。** Grooveでは23,205候補のうち、
属性間で増減が混在する11,507組、難易度の向き・差を満たさない7,693組、
リズム・骨格の基準を満たさない3,967組などが除外された。
採用数のために閾値を緩めていない。Grooveでの性能や3データセット全体の代表性を示すデータとは扱わない。
固定格子上の一致、同一曲・同一周期位置、全5属性非増加という選択の影響を受ける。
itestも76例と小さく、単独で安定した汎化性能を測れるとは限らない。

入力の基点は `linear-04/revise-attribute` の `fd6e4e2`。実行ログは
`output/pairdata_v1/run.log`、テストログは同ディレクトリに保存した。
検証対象索引のSHA-256は `ff090af46b4e683d1f41c3386f645fe762e1fe0f7da4040e35aeb2a7cb8f00e6`。

## 検証と解釈

全件検証では、全ペアの現在・前後小節を原譜へ照合し、原文脈と再接続後の生スコア、
クラス、難易度差、各類似度を再計算する。シャードのチェックサム、ペアの一意性、
現在小節の内容と曲IDの分割間重複も確認する。

テストではHi-hat簡略化、骨格を変えたSnare、属性間の増減混在、テンポ・位置の不一致、
無音、重複、極端な速度、再接続後のKick連打、曲内反復、分割間共有、再開バッチの破損を扱う。

関連テストは65種類成功（最初に63件、重複・再開の2件を追加後に新規17件を再実行）。
両CLIの `--help` も成功。200曲の試験では194ペアを生成し全件検証した。

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python -m pytest -q \
  tests/test_pairdata.py tests/test_drum_difficulty_v2.py \
  tests/test_build_drum_collection.py tests/test_tokenization_policy.py \
  tests/test_tokenization_mode_validation.py
```

既存ローダーの `tests/test_drum_dataloader_difficulty_alignment.py` は、前タスクと同じ
`test_bar_level_difficulty_expands_to_token_level_sequence` と
`test_mismatch_between_bar_count_and_difficulty_count_fails_fast` の2件が失敗し、1件が成功した。
今回の変更対象外であり、全テスト成功とは報告しない。基準YAML・モデル・既存ローダーは変更していない。

音楽的類似度・文脈・難易度はルールに基づくため、このデータは**擬似ペア**である。
人による編曲の正解、聴感上の同等性、演奏難易度の実技検証、他トラックとの整合性は未確認。
骨格類似度の閾値を通ったことだけで「骨格を完全に保持した」と結論しない。
また、全属性非増加の選択により、属性間のトレードオフを伴う実際の編曲は含まれにくい。
手動レビューや実演評価と組み合わせる研究用の教師候補として使用する。
