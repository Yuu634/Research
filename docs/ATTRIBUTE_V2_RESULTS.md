# 難易度属性v2の実装・ラベリング結果

実施日：2026-09-30。ユーザー承認後、`linear-02/data-create` の `f2e3d5e` を基点に
`linear-04/revise-attribute` で実施した。[承認済み算出式](ATTRIBUTE_FORMULA_REVIEW.md)を固定して使用した。

## 実装の範囲

- `src/data/drum_difficulty_v2.py`：5属性の改良式と、検証用の `s_rhythm`。
- `scripts/preprocess/label_drum_difficulty_v2.py`：生スコア、境界推定、PKL生成、全件検証。
- `scripts/evaluate/evaluate_rhythm_attribute_v2.py`：Zenodo資料による反復性指標の外部診断。

原トークンのテンポ・量子化・強弱表現を使い、全実小節にラベルを付与する。
技術・手足非同期・手の打撃・足の打撃は秒当たりの量、移動は配置距離／秒の最小最大値である。
直前小節の打撃を文脈として使用する。移動は2本の手の割当を動的計画法で全探索した下限であり、
現実の運指・疲労・身体姿勢を推定したものではない。

既存5属性の計算器、基準YAML、モデル、チェックポイントは変更していない。
`s_rhythm` は小節辞書に保存するが、現行モデルの条件入力には使用されない。
v2クラスで学習する場合は別設定・別チェックポイントを用いる。既存チェックポイントのv1条件値と
同じ意味として置き換えることはできない。

## データとクラス境界

入力は `data/tokens/drum_collection_v1/` と、対応するメタデータ内の有効な分割リスト。
105,477個の全トークンファイルのうち、分割対象の83,602曲を処理した。
曲IDと元のtrain/val/test/itestの所属を保持し、再分割はしていない。

出力先：

- `data/processed/drum_collection_difficulty_v2/`：ラベル付きPKL、トークン方式メタデータ。
- `data/metadata/drum_collection_difficulty_v2/`：語彙、分割リスト、境界、監査情報、生スコア。
- `output/revise_attribute_v2/`：実行ログ、人工例、外部診断結果。

PKLは `(bar_positions, token_indices, difficulty_classes)` の3要素。
小節辞書には `s_tech / s_indep / s_hand / s_foot / s_move / s_rhythm` の整数クラス0〜7を保存する。
元の小節位置とトークン列は変更しない。

0点はクラス0。正値は有効trainの重み付き経験分布を7分割する6境界からクラス1〜7へ写す。
重みはデータセット間で均等、各データセット内では曲間で均等、曲内では小節間で均等とした。
同点を乱数で分離せず、境界と等しい値は下側クラスに入れる。val/test/itestは境界推定に使用しない。
これは学習集合に対する相対クラスであり、演奏者の絶対的な技能等級ではない。

有効trainでは6属性とも全8クラスに値がある。分割・データセット別のクラス度数は `summary.json` に保存した。
移動0は2つの固定打点に手を分担できる場合なども含み、演奏全体の難易度0を意味しない。

有効出力にも同一位置・同一楽器の重複フラグがある曲が5,322曲、該当小節が85,534小節残る。
打撃数を暗黙に減らさず原トークンに従って算出したため、足の最大値は約210打／秒相当となる。
これを人間の実測速度と解釈しない。2手の移動が計算できることだけで、すべての身体的制約を満たすとは限らない。

手の速度について、Q80・承認済みQ90・最大値を用いたスコアの全小節平均はそれぞれ
6.033・7.631・9.340。分位点の選択による差は残る。Kick・HHペダル別の同様の感度分析も保存した。

### 除外の意味

両手の同時打撃の割当が不能な小節を含む曲は、承認済みの方針どおり曲単位で除外した。
計算不能な移動スコアを0へ置き換えてはいない。これは演奏不能の判定ではなく、
トークンの量子化、ドラムトラックの重畳、打撃の重複なども含めた、今回のモデルの適用限界である。
原データは保持し、除外ID・理由・小節番号は `manifest.jsonl`、算出済みの他属性と構成値は
`scores.sqlite` に保存した。後者のpayloadはzlib圧縮したpickleで、列の順番は `identity.json` に記録する。

Lakh・Groove2Grooveで除外割合が大きいため、出力集合は元の譜面分布を代表しているとは限らない。
密な打撃や重畳譜面が除かれる方向の選択バイアスがあり、元集合全体へ結果を一般化しない。
再利用時も、全曲に正しい難易度が付与されたデータとして扱わず、除外集合と区別する必要がある。

## s_rhythmの外部診断

[Zenodo v4の40刺激](https://zenodo.org/records/10728042)を使用した。
対象は聴いて感じる複雑さのBradley–Terry係数で、身体的な演奏難易度の正解ではない。
式や係数をこの評価値に合わせて調整していない。

各刺激の先頭4小節（`0 <= Beats < 16`）を1拍24分割へ切り捨て量子化し、
Kick・Snare・その他の3系列について、承認済みのLZ78式を小節ごとに計算して平均した。
末端の余分な拍は含めない。2,679打撃中3打撃が格子外、最大量子化誤差は0.03833拍。
四捨五入に変えた感度分析でも、今回の相関は同じだった。

| 指標 | 知覚的複雑さとのSpearman相関 | 刺激単位bootstrap 95%区間 |
|---|---:|---|
| 今回のLZ反復性 | 0.643 | [0.385, 0.822] |
| 同じ4小節内の音数 | 0.622 | [0.364, 0.807] |
| 配布資料の音数 | 0.621 | [0.363, 0.806] |
| 配布資料のSyncopationIndex | 0.690 | [0.502, 0.819] |
| 配布資料のRevisedSyncopationIndex | 0.763 | [0.577, 0.861] |
| 配布資料のBDM指標 | 0.748 | [0.569, 0.851] |

再標本化は40刺激を単位に2,000回、乱数seedは20260930。
LZのKendall tau-bは0.489。公開対照値には区間定義の差があるため、この表だけで優劣を断定しない。
相関差の検定は行っていない。

今回のLZと音数とのSpearman相関は **0.943** と高い。
人工例でも、Kickを位置 `[0,12,24,36,48,60,72,84]` に置く等間隔8打と、
`[0,6,18,30,48,66,78,90]` に置く不等間隔8打が、どちらも **0.114322** となった。
等間隔4打は0.045729、等間隔16打は0.182916で、規則的でも音数によって増加した。

したがって、知覚的複雑さとの正の関連は見られるが、音数から独立したリズム難易度、
または細かな不規則性を識別する性能は確認できない。**検証用の反復性記述子として保持し、
6番目の演奏難易度条件としての採用は保留する。** 5属性についても演奏者による実技検証は未実施である。

## 検証

新規17テストでは、手計算例、BPM倍増、通常音追加で奏法負荷が薄まらないこと、
同時打撃の順序不変性、前小節の文脈、LZの終端処理、末尾小節、重み付き境界を確認した。
移動DPは独立した全割当列挙とも比較し、計算不能と0点を区別した。
未知トークン・不正位置・途中EOSの拒否、重複の監査、テンポの異なる小節間の秒換算も確認した。
関連の収集・トークン方式31テストと合わせて **48件成功**（初回43件、境界例追加後に新規17件を再実行）。

```bash
TMPDIR="$PWD/output/revise_attribute_v2/tmp" python -m pytest -q \
  tests/test_drum_difficulty_v2.py tests/test_build_drum_collection.py \
  tests/test_tokenization_policy.py tests/test_tokenization_mode_validation.py \
  --basetemp=output/revise_attribute_v2/tmp/regression
```

変更前の基点でも `tests/test_drum_dataloader_difficulty_alignment.py` に2件の既存失敗があった。
`test_bar_level_difficulty_expands_to_token_level_sequence` は小節ラベルの期待形状との不一致、
`test_mismatch_between_bar_count_and_difficulty_count_fails_fast` は期待する例外が発生しない。
今回これらの既存ローダー挙動は変更しておらず、全テスト成功とは報告しない。

両CLIの `--help` は成功。200曲のスモーク試験では133曲を生成し、全件内容検証に成功した。
本番の検証結果は以下に記載する。

本番 **35,106曲・3,256,333小節** の全出力PKLを再読み出し、以下を確認した。

- 元のトークン列・小節位置と保存済みハッシュが一致。
- 末尾を含む全実小節に、6属性・整数0〜7のラベルが対応。
- 生スコア・構成値が有限で、各ラベルが保存済み境界と対応。
- 出力一覧と分割リストが一致し、元分割を保持。分割間のID重複なし。
- 生成時の出力SHA-256と一致。

さらに固定ID条件で選んだ31曲は生スコアも再計算して一致した。
生スコアの再計算はこの部分集合であり、全曲について再計算したわけではない。
全体分割・データセット別分割の計14リストも、最終manifestから別途照合した。
既存 `DrumTransformerDataset` では全10データセット／分割から1曲ずつ読み込み、
encoder `(16, 128)`、decoder `(1280,)`、5属性の小節・トークン条件を確認した。
`s_rhythm` が現行条件入力へ混入しないことも確認した。

全件検証は `data/metadata/drum_collection_difficulty_v2/validation.json`、
ローダー確認と追加監査は `output/revise_attribute_v2/loader_validation.json`・`final_audit.json` に保存した。
実行終了コードは0。算出式とパイプラインのハッシュは開始時と一致する。

## 再実行

リポジトリ直下で、収集済みv1データと分割・語彙を用意して実行する。
データ、外部資料、重み、ログ、診断JSONはGitに含めない。

```bash
python -m scripts.preprocess.label_drum_difficulty_v2 --help
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 \
  python -m scripts.preprocess.label_drum_difficulty_v2 --workers 24
```

既定の処理は `score → bounds → label → validate`。
同じコード・入力・出力設定で再実行すると保存済み生スコアと生成済みPKLから再開する。
ファイルを削除・編集した出力先の自動修復は行わない。
実行中は監査用の長時間SQLite読み取りを並行させない。今回、並行読み取りによる書き込みロックで
生成が一度中断したが、読み取りを終了し、同じコマンドで保存済みの進捗から再開した。
初回ログは `output/revise_attribute_v2/run.log`、再開後は `resume.log` に保存した。
コード、入力メタデータ、語彙などが変わった場合は別の `--output` と `--meta` を指定する。
コードと入力のSHA-256、Python・NumPyのバージョンは `identity.json` に保存する。

外部診断ではZenodoの `Data_240229.zip` を取得し、次を実行する。
`rdata` は通常のラベリングには不要。隔離先への `--no-deps` インストール例は、
NumPy・pandas・xarray・typing_extensionsがすでに利用可能な環境を前提とする。
新規環境では `--no-deps` を外して依存もインストールする。

```bash
python -m pip install --no-deps --target output/revise_attribute_v2/deps \
  -r requirements_attribute_v2.txt
python -m scripts.evaluate.evaluate_rhythm_attribute_v2 \
  --archive output/revise_attribute_review/Data_240229.zip
```

使用版はPython 3.13.5、NumPy 2.1.3、SciPy 1.15.3、pandas 2.2.3、xarray 2025.4.0、rdata 1.0.0。
外部資料のMD5は `b4be12a160658ba49486278237da2ce1`。
資料のSHA-256と診断スクリプトのハッシュも診断結果に保存した。

今回の5属性式は、[参照論文](https://arxiv.org/html/2408.00473v1)の考え方を参考にした本研究の提案であり、
論文の式や性能をドラムへそのまま移したものではない。
