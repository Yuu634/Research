# Implementation Tasks

- [x] 1. モード選択と実行境界の統一制御を実装する
- [x] 1.1 モード妥当性判定と統一エラー契約を整備する
  - 前処理・学習・生成で参照する許可モード集合を単一の定義として扱う。
  - 不正モード入力時は処理を開始せず、利用可能モード名を含む診断を返す。
  - 空値や想定外フォーマットの入力を同一カテゴリの入力エラーとして扱う。
  - _Requirements: 1.2, 1.5, 6.2_

- [x] 1.2 前処理・学習・生成のモード解釈を同一ルールへ揃える
  - 実行開始時点でモードを確定し、同一ジョブ中の混在を禁止する。
  - 下流処理へ渡すモード情報を正規化し、分岐条件の揺れを排除する。
  - 既存の設定駆動フローを維持し、モード切替の再現性を担保する。
  - _Requirements: 1.1, 1.3_

- [x] 1.3 成果物と実行モードの対応関係を起動前に検証する
  - データセット生成時モードと実行時モードの一致確認を必須化する。
  - 不一致時は処理を停止し、期待値と実値を含む説明可能なエラーを返す。
  - モード不一致の判定結果をログへ記録し、再現検証できるようにする。
  - _Requirements: 1.4, 6.2_

- [x] 2. 共通ポリシーで velocity と Position の意味論を統一する
- [x] 2.1 標準3段階 velocity 分類を共通契約として固定する
  - 全モードで同じ判定結果を返す速度分類ルールを導入する。
  - 閾値は Ghost <15、Normal <100、Accent >=100 として固定する。
  - 境界値を含む入力で分類結果が不変になることを確認する。
  - _Requirements: 2.2, 4.6_

- [x] 2.2 standard 準拠 Position 量子化を共通契約として固定する
  - 1拍24分割を canonical とする量子化規則を統一する。
  - REMI と CP の Position が standard と同一算出式になるよう揃える。
  - 非 Note の CP イベントでは Position PAD を使う規則を固定する。
  - _Requirements: 4.3, 4.7_

- [x] 2.3 standard モードの後方互換を保護する
  - 既存の standard 意味論を変更せず、新ポリシー導入の影響を局所化する。
  - 既存資産を追加移行なしで読み込める互換条件を維持する。
  - standard 実行時に remi/cp 専用必須要件を要求しないことを保証する。
  - _Requirements: 3.1, 3.2, 3.3, 3.5, 6.4_

- [x] 3. REMI ドラム表現を共有ポリシー準拠で実装する
- [x] 3.1 REMI の時間・打点イベント生成をドラム用に確立する
  - ドラム入力から REMI 互換イベント系列を安定して生成する。
  - ベロシティは共通3段階分類を使い、連続値表現を必須にしない。
  - Position は standard 準拠量子化で一貫して算出する。
  - _Requirements: 2.1, 2.2, 2.3_

- [x] 3.2 REMI の処理対象をドラムに限定する
  - 非ドラム楽器トラックを処理対象外として一貫した扱いにする。
  - ドラム限定運用での入力検証と除外処理の挙動を明確化する。
  - ドラム限定ポリシーが下流へ伝播するメタ情報を保持する。
  - _Requirements: 2.4, 2.5, 6.1_

- [x] 4. CP 四肢6次元表現と演奏意味論を完成させる
- [x] 4.1 CP の固定長6次元スキーマと構造イベント規則を実装する
  - すべてのイベントを [Type, Position, Hand1, Hand2, Right_Foot, Left_Foot] で表現する。
  - Bar/Beat など構造イベントでは Position と四肢次元を NA/PAD として扱う。
  - 小節アンカーとしての Bar イベントを常に提供する。
  - _Requirements: 4.1, 4.2, 4.4, 4.5_

- [x] 4.2 CP Note イベントに standard 準拠 Position/velocity を適用する
  - Note イベントの Position を standard と同一規則で解釈する。
  - velocity は共通3段階分類を適用し、CP 固有閾値を持たない。
  - Note と構造イベントで Position の扱いが混同しない整合チェックを追加する。
  - _Requirements: 4.3, 4.6, 4.7_

- [x] 4.3 四肢トークンの演奏意味論を維持する
  - 手で演奏する打点を Hand1/Hand2 に割り当てる規則を維持する。
  - ハイハットの open/close 状態と Left_Foot 表現の対応を保持する。
  - 両足バスドラムの推奨順序規則を Right_Foot/Left_Foot で維持する。
  - _Requirements: 5.1, 5.2, 5.3, 5.4, 5.5_

- [x] 5. 成果物メタデータと互換性ガードを強化する
- [x] 5.1 成果物の mode/schema/version 識別情報を解決可能にする
  - データセットと語彙の双方からモード識別情報を取得可能にする。
  - スキーマ判定に必要な識別子を学習・生成の起動時に参照できる形で保持する。
  - 判定不能な成果物を明示的な不整合として扱う。
  - _Requirements: 6.1, 6.5_

- [x] 5.2 学習・生成起動時の互換性ガードを fail-fast 化する
  - モード不一致やスキーマ不一致を開始前に検出して停止する。
  - エラーには原因分類と期待値/実値を含め、修正方針を判断可能にする。
  - 非選択モード起因の追加要求を standard フローへ波及させない。
  - _Requirements: 1.4, 6.2, 6.4_

- [x] 6. テストと統合検証で受け入れ基準を固定する
- [x] 6.1 (P) 共通ポリシーとモード検証の単体テストを整備する
  - velocity 境界値と Position 量子化/PAD の判定を網羅する。
  - 正常系・異常系のモード検証結果を固定し、回帰を防止する。
  - CP スキーマの必須項目と系列長整合を検証する。
  - _Requirements: 1.2, 2.2, 4.3, 4.6, 4.7, 6.5_

- [x] 6.2 (P) モード別の統合テストを整備する
  - REMI 前処理から下流読込まで、速度/Position 統一を含めて検証する。
  - CP のトークン化から学習入力までの一連経路を検証する。
  - 設定と成果物のモード不一致検出が期待通り停止することを確認する。
  - _Requirements: 1.1, 1.4, 2.1, 2.5, 4.1, 6.2, 6.3_

- [x] 6.3 standard 回帰と E2E スモーク検証を実施する
  - 既存 standard 資産を用いて互換性を確認し、期待値差分を監視する。
  - preprocess → train → generate の最小パイプラインを3モードで実行確認する。
  - remi/cp 追加後も standard の既存テスト期待値が維持されることを確認する。
  - _Requirements: 3.1, 3.2, 3.4, 4.5, 6.4_
